# 0.7.1 — 2026-08-06

## Added

- **`gbif_search_datasets.publishingOrg`** — the organization whose data a dataset is, alongside the existing `hostingOrg` (the organization whose installation serves it). `hostingOrg` was the only organization filter, so the documented `gbif_search_publishers` → `gbif_search_datasets` chain returned zero for any organization that publishes through someone else's installation, which is most of them: of the first 25 GB organizations the registry lists, all 25 host no datasets while 13 publish one or two. Butterfly Conservation (`0d72dd7f-6f05-46af-85c2-8b6e77ce5534`) publishes 3 datasets and hosts none; the National Biodiversity Network (`07f617d0-c688-11d8-bf62-b8a03c50a862`) hosts 984 and publishes 1. Forwarded by `GbifService.searchDatasets`. ([#52](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/52))
- **Both-organization-filter notice** — GBIF intersects `publishingOrg` and `hostingOrg` rather than combining them, so the same key in both fields matches only what that organization both published and serves. The empty-result notice on `gbif_search_datasets` names the intersection when both were applied.

## Changed

- **`publishingOrg` and `hostingOrg` are validated against the lowercase 8-4-4-4-12 hex form** whenever present, failing as `invalid_filter`. `/dataset/search` matches these two parameters case-sensitively, unlike every other UUID this server forwards: `publishingOrg=0D72DD7F-6F05-46AF-85C2-8B6E77CE5534` returns 0 where the same key lowercased returns 3. `isGbifUuid` keeps its case-insensitive regex for `datasetKey`, whose routes resolve either case. ([#52](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/52))
- **Chaining guidance points at `publishingOrg`** across both tool descriptions, the `key` output field on `gbif_search_publishers`, the server-level `instructions`, `README.md`, and `docs/design.md` (decision 15).

## Fixed

- **Every optional filter on `gbif_search_occurrences`, `gbif_count_occurrences`, `gbif_occurrence_facets`, `gbif_search_species`, `gbif_search_datasets`, `gbif_search_publishers`, and `gbif_match_species` now fires its guard on presence instead of on a non-blank value**, so a blank or whitespace-only value fails as `invalid_filter` rather than being dropped. Guard and forward both tested `?.trim()`, which cleared the filter and answered the whole unfiltered scope while the caller believed the query was narrowed. On a `taxonKey=212` + `country=GB` + `occurrenceStatus=PRESENT` scope of 60,290,950 records, a blank `stateProvince`, `year`, `geometry`, `decimalLatitude`, `decimalLongitude`, or `coordinateUncertaintyInMeters` each returned all 60,290,950 — against 47,672,439 for `England` and 4,179,801 for `2020`. Every value the old test forwarded is still forwarded byte-identically, untrimmed; omitting a field remains the way to leave a filter off. ([#53](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/53), [#54](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/54))
- **`datasetKey`** on the three occurrence tools and `gbif_search_species` reaches the same rejection a malformed key already drew. `/occurrence/search?datasetKey=` answers 200 with the unfiltered total, so `gbif_count_occurrences` on `taxonKey=212` returned the same 2,351,689,943 with `datasetKey: ""` as with the field omitted, where a real key returns 1,775,781,186. ([#53](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/53))
- **`gbif_search_publishers.country`** rejects the empty string, which `/organization` reads as no filter and answers with all 3,561 registered organizations against 223 for `GB`. Only the empty string is guarded there — the registry resolves the parsed country, so `gb` and `GBR` are correct answers, and whitespace alone already draws a `400 Cannot parse … into a known Country` the service tags `invalid_filter`. ([#53](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/53))
- **`gbif_match_species.kingdom`** rejects a blank value, which `/species/match` drops: `Parus major` with `kingdom=` resolves to usage key 9705453, exactly as omitting the field does, where `Plantae` resolves to 9711704 — an undisambiguated answer indistinguishable from a disambiguated one. The tool gains an `invalid_filter` contract entry for it. ([#54](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/54))
- **New `firstBlankFilter` helper** in `src/mcp-server/tools/utils.ts` names the offending field; each handler throws its own `invalid_filter` so the tool's declared recovery hint rides along. Each tool's `invalid_filter` `when`/`recovery` wording and the affected field descriptions state that a blank value is not a way to skip a filter.
- **`kingdom`, `family`, and `genus` on `gbif_search_species` are deliberately excluded** from the rule — `/species/search` implements none of the three, answering identically to an invented parameter name at every value, so there is no filter for a blank to drop. Tracked separately as [#55](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/55).
