# 0.7.0 — 2026-08-06

## Changed

- **`country`** on `gbif_search_occurrences`, `gbif_count_occurrences`, and `gbif_occurrence_facets`, and **`publishingCountry`** on `gbif_search_datasets`, now carry a `^[A-Z]{2}$` Zod pattern — matching the `publishingCountry` pattern already on the three occurrence tools. `/occurrence/search` and `/dataset/search` parse a country code and then match the verbatim stored string, so a form that parses but isn't stored — lowercase, mixed case, alpha-3 (`gb`, `Us`, `USA`) — previously answered 200 with zero rows instead of an error. The pattern turns that silent wrong answer into a local validation error naming the accepted form; a code the pattern accepts but GBIF doesn't assign (`XX`) still draws GBIF's own HTTP 400, tagged `invalid_filter` with a recovery hint pointing at the `COUNTRY` or `PUBLISHING_COUNTRY` facet. ([#50](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/50), [#51](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/51))
- **`gbif_search_publishers.country`** stays an unpatterned string, deliberately — its `/organization` route resolves the parsed country rather than the stored string, so `gb`, `gbr`, and `GBR` already return the same organizations as `GB`. Applying the same pattern there would reject values that currently answer correctly. ([#50](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/50), [#51](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/51))

## Fixed

- **Empty-string `country`/`publishingCountry`** on all four patterned fields no longer silently drops the filter. Each handler previously guarded with `?.trim()`, so `country: ""` or `publishingCountry: ""` passed schema validation and then returned an unfiltered result — `gbif_search_datasets` with `publishingCountry: ""` returned all 123,527 indexed datasets to a caller who believed they'd filtered by country. The empty string now fails the `^[A-Z]{2}$` pattern, and each handler guard drops to a plain truthiness check. ([#50](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/50), [#51](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/51))

## Breaking

- **A whitespace-padded uppercase code (` GB `) that previously worked now fails validation.** GBIF trims the value upstream on both `/occurrence/search` and `/dataset/search`, so a padded code answered correctly before this release. The new pattern rejects any surrounding whitespace — the schema states one accepted form rather than one form plus whatever GBIF happens to tolerate. Every other newly-rejected form (lowercase, mixed case, alpha-3, empty string) previously returned a silent zero-record or unfiltered result, not a real answer, so those are fixes rather than breaks. Callers sending a padded code must strip it before calling.
