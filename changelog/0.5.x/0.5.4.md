# 0.5.4 — 2026-08-06

## Changed

- **`GbifService.getJson`** — a hung request now aborts with a `TimeoutError` `DOMException` matched by identity, producing a `Timeout` error that names GBIF and the deadline instead of a raw, unclassified `AbortError`.

## Fixed

- **Upstream HTTP 400s** — `GbifService` now builds the thrown error through `gbifHttpError()`, which folds GBIF's own explanation into the message (so `content[]` states the cause, not just the status), drops the redundant `data.url`, and attaches `reason: 'invalid_filter'` with a `recovery.hint`. An HTML rate-limit/outage body is kept out of the message. ([#38](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/38))
- **`gbif_get_dataset`, `gbif_search_occurrences`, `gbif_count_occurrences`, `gbif_occurrence_facets`, `gbif_search_datasets`, `gbif_search_species`, `gbif://dataset/{datasetKey}`** — every UUID-shaped input (`datasetKey`, `hostingOrg`) is now checked against the 8-4-4-4-12 hex form before a request goes out, failing locally as `invalid_filter` with a hint. Closes the `gbif_count_occurrences` case where `/occurrence/count` answered HTTP 200 with `0` for a malformed `datasetKey` — a confident wrong total rather than an error. `gbif_search_occurrences`'s dead `upstream_error` contract (declared `InternalError`, no throw site) is replaced by `invalid_filter` (`InvalidParams`). ([#38](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/38))
- **`gbif_get_dataset`, `gbif://dataset/{datasetKey}`** — `recordCount` is no longer permanently absent. `/dataset/{key}` never supplies `numRecords` or `recordCount`, so both surfaces now fill it via a bounded secondary `/occurrence/count?datasetKey=` call (`resolveDatasetRecordCount()`) for `OCCURRENCE`-type datasets — no retries, 3s deadline — and degrade silently to absent on failure, timeout, or any other dataset type. ([#40](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/40))
- **`gbif_search_occurrences`** — `PAGINATION_CAP` corrected from `99_000` to `100_001`, GBIF's real `offset + limit` boundary; the 99,001–100,001 band, previously rejected locally, is reachable again. The rejection message now names `100_001` instead of "~100,000," a value the failing sum could sit under. ([#42](https://github.com/cyanheads/gbif-biodiversity-mcp-server/issues/42))
